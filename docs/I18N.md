# Saltcorn Feldspar — Internationalisation

A design proposal for one translation facility spanning the Rust core, the admin SPA, the
Saltcorn UI view runtime and the React (and Vue, and anything else) applications this server
builds. It is the source document for the i18n milestone; the task list is
[../TODO.md](../TODO.md).

---

## 1. Three kinds of string, and what changed since v1

Saltcorn 1 distinguished three populations of translatable string, and the distinction holds
here because it is about **who wrote the string and when**, not about any particular
technology:

| | Who wrote it | When | Where it lives | Who translates it |
|---|---|---|---|---|
| **A** | us | at release | the source tree | us, once, shipped |
| **B** | the admin (or their coding agent) | while building an app | the app's definition | the admin, per installation |
| **C** | the end user | while using the app | a table row | nobody, usually |

v1's answers: **A** through the [`i18n`](https://www.npmjs.com/package/i18n) npm package —
every string wrapped in `req.__("English goes here")`, the library emitting a JSON file per
enabled locale, an LLM filling them in, all of it committed to git and shipped in the npm
package. **B** through a per-view-template `getStringsForI18n` that *collected* the admin's
own strings out of view configurations and builder layouts into a screen where they could be
typed in or LLM-filled per locale. **C** through `localizes_field`: a String field could
declare itself the `fr` translation of another String field on the same table
(`packages/saltcorn-data/base-plugin/types.ts`), and the row layer picked the right column.

Three things changed in Feldspar, and between them they decide most of this design:

1. **The core is Rust and the UI is React.** A string is either produced by a Rust crate or
   written into a `.tsx` file, and there is no longer one library that can serve both. Whatever
   is chosen has to be read by two runtimes.
2. **Type B strings are now mostly source code.** In v1 an admin's label lived in a view's
   `configuration` JSON, which the server could walk. Here the optimised case is the `react`
   framework: the admin's labels are string literals inside `src/routes.tsx`, written by a
   person in the IDE or by the coding agent. Nothing walks that but a parser. (Saltcorn UI
   applications keep v1's shape exactly, and keep v1's answer.)
3. **There is an LLM in the building.** `sc-llm` is configured, has provider records, and is
   already used by agents and the copilot. v1's "get an LLM to translate them" was a manual
   step outside the product; here it is an endpoint and a button.

What stays true: the end user of a well-built application sees *mostly* B strings, but not only
B strings — "Incorrect password", "That file is too large", the validation message under a field
— and an admin deserves the admin UI in their own language just as much as an end user deserves
the app in theirs.

## 2. What the field looks like in 2026

### Message formats

| Format | Placeholders | Plurals | Rust | JS/React | Verdict |
|---|---|---|---|---|---|
| **ICU MessageFormat 1** | `{name}` | inline `{n, plural, …}` | no mainstream Rust formatter (`forest-rs/message-format` is the nearest, and niche) | `intl-messageformat` (react-intl), Lingui | *the JS lingua franca; no Rust half* |
| **MessageFormat 2.0 (CLDR)** | `{$name}` | `.match` | ICU4X: not stable | `messageformat` v4 | **too early** — the spec went Stable at CLDR 47, the C++ implementation is still technology preview and the Rust one is not there at all |
| **Fluent (`.ftl`)** | `{ $name }` | select expressions | `fluent-bundle`, mature | `@fluent/bundle`, `@fluent/react` | the only format with a *good* implementation on both sides. Cost: identifiers are mandatory, and extraction from source is not a thing Fluent does |
| **gettext (`.po`)** | `%s` / `%(name)s` | `nplurals` header | `gettext-rs` (C) / `gettext` | `gettext.js` | excellent tooling (xgettext, Weblate, Crowdin), 1980s plural model, and a binary-ish format nobody hand-edits |
| **i18next JSON** | `{{name}}` | `key_one`/`key_other` via `Intl.PluralRules` | none, but the format is a flat JSON object | i18next + react-i18next | trivial on both sides because there is almost nothing to it |

### React libraries

`react-i18next` (~22 kB gz, biggest ecosystem, key-based, non-standard format), `react-intl`
(ICU-standard, similar weight), `Lingui` (~10 kB, macro + compiler, source text as the message,
extraction built in), `next-intl` (Next-shaped). All four assume they own the app's build
pipeline: extraction is a Babel/SWC plugin or a CLI run inside the project.

### Rust crates

`fluent-bundle` (real, maintained, Fluent-only), `rust-i18n` (a `t!` macro over YAML/JSON,
compile-time embedding, no CLDR plurals), `icu` / ICU4X (the primitives: `icu_locale_core` for
BCP-47, `icu_plurals` for CLDR plural categories — both current and both usable without the
rest), `gettext`.

### The two constraints that decide it

**(i) One catalogue has to be readable by two runtimes and editable by a non-programmer.** That
rules out anything whose reference implementation exists on only one side (ICU MF1's inline
plural syntax, MF2 today) and anything a translator cannot open (`.mo`).

**(ii) Extraction cannot live in the application's build.** The admin UI must be able to show
"here are the strings your application uses" for an app it has never built, whose `package.json`
we do not control, whose framework might be Vue, and which may be mid-edit by an agent. Every
JS i18n library's extraction story is a plugin in *that project's* bundler. Ours has to run in
the server, over the source tree, on demand.

Constraint (ii) is the one nobody else has, and it is the reason this proposal does not simply
adopt Lingui or react-i18next. It is also cheap for us to satisfy that nobody else can: the
workspace already links **tree-sitter with the JavaScript, TypeScript and TSX grammars**
(`sc-repomap`, for the coding agent's repo map). Parsing an application's source in Rust is an
afternoon, not a project.

## 3. The design in one page

```
                      ┌──────────────────────────────────────────────┐
                      │  sc-i18n  (layer 0)                          │
                      │  Locale · negotiation · Catalog · format()   │
                      │  plural select · t! · extract (tree-sitter)  │
                      └───┬───────────────┬───────────────┬──────────┘
        A (Rust)          │               │               │   B (app source)
  crates/**  t!(loc,"…")  │               │               │
  locales/{loc}.json ◄────┘               │               └────► <project>/locales/{loc}.json
  compiled into the binary                │                      in the app's file store
                                          │
        A (admin SPA)                     │                B (Saltcorn UI)
  ui/admin/src/locales/{loc}.json         │          _fd_translations rows, per application
  lazily imported by the bundle           │          (a view config is not a file)
                                          │
                                          │                B (shared, every application)
                                          │          _fd_translations rows, application NULL,
                                          │          served under each app's own (app wins)
                                          │
                                   the same JSON:
                              { "English source": "translation" }
```

Four catalogue **domains** (`core`, `admin`, `builder`, and one per application), one **format**,
one **runtime contract** implemented twice (Rust `sc_i18n::format`, TypeScript
`feldspar/messages.ts`) and held to it by a shared fixture file, one **extractor** (Rust,
tree-sitter), one **translator** (`sc-llm`, behind a `Translator` seam so `sc-i18n` stays at
layer 0).

## 4. The decisions

### D1. The message id is the English source text

`t("Incorrect password")`, not `t("auth.bad_password")`.

- It is what v1 did, and the vendored v1 view patterns call `req.__("Preset %s")` — with keys,
  every one of those call sites would have to be rewritten in code we deliberately do not own.
- **A missing translation renders correct English**, not `auth.bad_password`. For a facility
  whose normal state is "the admin has translated 60% of their app", the failure mode is the
  design.
- An LLM translating `"Delete {name}?"` has the context; an LLM translating `"tbl.del.confirm"`
  has none.
- Extraction is mechanical: the literal at the call site *is* the record.
- A coding agent writes `t("Add a task")` without being told a key convention, which matters
  because the coding agent is how most B strings will be written.

The cost is real and is accepted: **changing the English orphans the translation.** Mitigation is
not deletion — the translation screen shows orphaned entries under "no longer used", keeps them in
the file, and offers them for a string that looks similar. The second cost is collision: one
English word with two meanings. `tc("verb", "Order")` disambiguates, storing the key as
`verb\u{4}Order` (gettext's `msgctxt` convention, so the file stays flat).

### D2. Placeholders are `{name}`, and a message is not a template

A message may contain `{identifier}` and nothing else. No expressions, no member access, no
function calls, no filters.

The product already has a `{{ }}` template language (`sc_expr::Template`: email subjects,
ownership formulae, a declared framework's paths), and reusing its sigil here would be a mistake
for one concrete reason: **in a Saltcorn UI layout, a text element's content is simultaneously a
translatable B string and a `{{ }}` template.** If a message placeholder looked the same, a
translator's `{{ user.email }}` would be indistinguishable from an interpolation the renderer is
supposed to evaluate, and the difference between "data from a translator" and "an expression this
server executes" is not one to leave to a parser. Single braces keep them visibly different, and
they are what ICU, MF2, Fluent, Lingui and every LLM already expect from a message.

`sc_i18n::format` is therefore ~60 lines and depends on nothing. `{{` escapes a literal brace. A
placeholder with no argument is left as written rather than rendered empty — a visible `{name}`
is a bug report; an empty string is a mystery.

**v1's `%s` survives inside the Saltcorn UI shim only.** `req.__("Preset %s", label)` keeps
positional substitution because the vendored patterns are what they are; the key in the catalogue
is the string with `%s` in it, and nothing else in the system sees that form.

### D3. Plurals are CLDR categories, selected by the platform

A catalogue entry is a string, or an object keyed by CLDR plural category:

```json
{
  "Incorrect password": "Mot de passe incorrect",
  "Delete {name}?": "Supprimer {name} ?",
  "{count} rows": { "one": "{count} ligne", "other": "{count} lignes" }
}
```

Selection uses the argument named `count`. In the browser that is `Intl.PluralRules`, which every
engine has had for years and which costs zero bytes. In Rust it is `icu_plurals` with
`compiled_data` — current, maintained, and the same CLDR data the browser is using. An entry that
is a plain string where the source expects plurals is used as written, because a locale with one
form is a locale with one form.

This is i18next's model minus the key-suffix spelling, and it is deliberately *not* ICU's inline
`{n, plural, …}`: inline plurals need a parser on both sides and give a translator a syntax to get
wrong inside a sentence they are already getting right.

### D4. One format, four domains, two homes

| Domain | Catalogue | Why there |
|---|---|---|
| `core` | `crates/sc-i18n/locales/{locale}.json`, `include_str!`-embedded | ships with the binary; a server with no database still has its messages |
| `admin` | `ui/admin/src/locales/{locale}.json`, `import()`-ed per locale | ships with the bundle, code-split so one locale is downloaded |
| `builder` | `ui/builder/src/locales/{locale}.json` | same, separate bundle |
| per application | **files** for an app with a project tree: `<project>/locales/{locale}.json`; **rows** in `_fd_translations` for one without (Saltcorn UI) | *an application's translations live wherever that application's definition lives* |

The last row is the one worth arguing. A `react` app's definition is its git repository; putting
its translations anywhere else means a clone that does not carry them, a coding agent that cannot
read them with the file tools it already has, and a backup story that has to remember them
separately. A Saltcorn UI app's definition is `_fd_views` and `_fd_pages`; it has no tree, so its
catalogue is a row — `_fd_translations`, one row per (application, locale), `name` = the locale
tag, `messages` a JSON object, deleted with the application, exactly as `_fd_library` is.

Both are behind one `CatalogStore` trait, so the admin API, the translation screen and the LLM
fill are written once.

**The shared catalogue** (TODO F6) is a third home for type B strings: `_fd_translations` rows
whose `application` is NULL, one per locale, in the same `messages` shape. It holds what many
applications say ("Sign in", "Password"). Lookup is **app → instance → key**, and it is merged on
the server in `GET {mount}/i18n/{locale}.json` (`sc_app::merged_app_catalogue`, also used by the
Saltcorn UI renderer), so the generated client and `useT` do not change. A key the app translates
wins, and an empty string in the app's catalogue counts as missing. Its locales are the
installation's `enabled_locales` less the source language. It has no source to extract, so its keys
are the union of what its locales hold. A shared save drops every mount's cached catalogues.

### D5. The server translates everything the server says

An admin's browser shows two kinds of English: literals in `ui/admin/src/*.tsx`, and text that
*arrived from the server* — an error message, a `FormField` label out of a provider's
`config_spec`, a settings section heading, a stream provider's one-sentence description.

The rule: **anything the server sends as human-readable text is translated by the server, against
the request's negotiated locale, before it is serialised.** The SPA's catalogue covers the SPA's
own literals and nothing else.

The alternative — ship the core catalogue to the browser and translate there — fails on the first
message with an interpolated value that was computed server-side, and makes every client of the
API (the MCP server, `feldspar` CLI, a generated app client) responsible for a job the server
already has the locale for.

Concretely this is `sc_i18n::translate_spec(&mut spec, loc)` on the handful of admin API paths
that serve declared specs, and `t!(loc, …)` at the places a message is produced for a human.

### D6. Extraction is a Rust pass over the source, not a step in anybody's build

`sc_i18n::extract` (feature `extract`, mirroring `sc-repomap`'s `grammars`) parses `.ts`, `.tsx`,
`.js`, `.jsx` with tree-sitter and reports every `t(...)`, `tc(...)`, `<T text="..."/>` call site:
the key, the file and the line. A call whose first argument is not a literal is an **extraction
error** naming file and line — `t(label)` cannot be translated and silently skipping it is how an
app ends up half-translated with nobody knowing.

Two things fall out for free:

- **The lint.** The same parse finds the opposite: a JSX *text node*, or a `label=`/`title=`/
  `placeholder=` attribute, holding a bare English literal that is not wrapped. `feldspar i18n
  lint` reports them, and the application's Translations screen shows the count. This is what
  makes "wrap the admin SPA's strings" a finishable job with a test at the end of it, rather than
  a sweep somebody eyeballs.
- **It works on an app that has never been built**, in any framework whose source is JS/TS,
  without npm, without the project's toolchain, and while an agent is halfway through editing it.

Rust-side keys are found by the same command with a small scanner over `t!(` call sites — a
macro, not a grammar, so a regex over the workspace is honest here and the test that it agrees
with the shipped `core` catalogue is what keeps it so.

### D7. An application's catalogue is served, not bundled

`GET {mount}/i18n/{locale}.json`, mounted *beside* the application's endpoint sets — the same
placement and the same reasoning as the stream observe socket (§13.2): an `EndpointSet` is a typed
request/response model and a catalogue is a file. The mount caches it with an ETag and re-reads on
save and on `SIGHUP`.

Bundling the catalogue into the app's build would be simpler and is wrong: an admin who fixes a
mistranslation would have to wait for a bundler, and "translate this app into Spanish" would be a
deploy. Serving it keeps v1's property that a translation is live, while the file stays in git.

Because the key is English (D1), the app renders correct English before the fetch lands. There is
no loading state and no flash of message ids.

### D8. One locale per request, negotiated once

In order: an explicit `?lang=`; the signed-in user's `language` column (new, nullable, on
`users`); the `lang` cookie (how an anonymous visitor to an application chooses); `Accept-Language`
matched against the enabled set with a proper fallback chain (`pt-BR` → `pt` → default); the
application's default locale; the server's `default_locale`. Computed once in the router, carried
on `AppRequest`, `ViewRequest` and the admin handler context. Responses carry `Content-Language`
and `Vary: Accept-Language, Cookie`.

**A locale is a value, passed explicitly** — `t!(loc, "…")`. Not a thread-local and not a
task-local: this server does work for a user on a task that no request owns (a trigger emailing a
customer), and an ambient locale is exactly the mechanism that would silently send that email in
the admin's language. The recipient's `language` column is the locale for that message, which is a
bug class v1 had and this does not.

Two config keys: `default_locale` and `enabled_locales`.

### D9. The LLM translates, and the machine checks it

One function, `translate_missing(catalog, locale, &dyn Translator)`, batching ~50 messages per
call as JSON. `Translator` is declared in `sc-i18n` (layer 0) and implemented over `sc-llm` in
`sc-server`/`sc-cli`, which is how every other seam in this tree is arranged.

The validation is the part that matters and it is not in the prompt: **a returned message whose
placeholder set differs from the source's is rejected** and left untranslated, with a warning
naming the key. So is one that lost its plural categories. An LLM that renames `{count}` to
`{nombre}` produces a string that renders a literal `{nombre}` in front of a user, and no amount
of prompt engineering is a substitute for checking.

Two surfaces, one function: `feldspar i18n translate --domain core --locale fr` at development
time, committed to git; a **Translate missing** button on an application's Translations screen at
run time, writing the app's own catalogue.

### D10. No new npm dependency: the runtime is generated

`src/feldspar/messages.ts` (framework-neutral: the catalogue fetch, `format`, plural select,
negotiation) and `src/feldspar/i18n.tsx` (React: `I18nProvider`, `useT()`, `<T>`) are **generated
by the server on every build**, beside `client.ts`, `hooks.ts` and `store.ts`, under the rule that
already governs that directory. A Vue framework declared by a module writes its own composable
over the same `messages.ts`, exactly as it writes `composables.ts` over the same `client.ts`.

Two reasons not to reach for react-i18next: it is 22 kB in an application whose dependencies are
the admin's business, and — the real one — its catalogue loading, its key conventions and its
plural spelling would become a contract this server has to agree with, in a project this server
does not build. The generated runtime is ~150 lines and is ours on both sides.

`<T>` handles the one thing a bare `t()` cannot — an element inside a sentence:

```tsx
<T text="Read the {link} before deleting" values={{ link: <a href="/docs">docs</a> }} />
```

### D11. Zero cost when unused

An application with no `locales` configured fetches nothing, ships one catalogue-free code path,
and behaves exactly as it does today: `t()` formats its argument and returns it. i18n is a thing
an admin turns on per application, not a tax on every app. The same holds for the server: with one
enabled locale, negotiation is a constant and `t!` is a lookup that misses.

## 5. What each population actually gets

### A — the product's own strings

**Rust.** Every message a human reads on a request path is wrapped: authentication and signup,
validation messages that reach a form, the application-facing 4xx sentences, the admin API's
refusals. `t!(loc, "…")` with the locale from the request. *Not* wrapped: System errors (§16) —
they go to the error log and to an admin reading a stack; a translated panic message helps
nobody and loses the string you would search for.

**The admin SPA.** Every literal in `ui/admin/src`, verified by the lint (D6). The locale picker
sits in the user menu, writes the user's `language` column, and sets `<html lang>`/`<html dir>`;
an RTL locale swaps in Bootstrap's `bootstrap.rtl.min.css`, which the dependency already ships.

**The builder.** `ui/builder`'s vendored `useTranslation` is already
`translations[phrase] || phrase` — a lookup keyed by the English phrase, which is D1 arrived at
independently by v1 — and what is empty is the map the server sends. Filling it from the
`builder` domain closes an item carried since the builder milestone.

### B — the admin's strings

**A code application** (the optimised case). The admin or the agent writes `t("Add a task")`,
importing `t` from `./feldspar/i18n`. The scaffold sets up the provider in `main.tsx`, `AGENTS.md`
and `SKILL.md` say to use `t()` for user-visible text, and the generated `README.md` in
`src/feldspar/` explains the catalogue. The Translations screen for that application lists every
extracted key with its translation per locale, a coverage number, the unwrapped literals the lint
found, the orphans, and the **Translate missing** button. Saving writes `<project>/locales/{locale}.json`
through the file store and tells the mount to re-read — no rebuild.

**A Saltcorn UI application.** v1's `getStringsForI18n` is vendored and intact on every view
pattern; a new `ViewRuntime::strings_for_i18n` call crosses the existing seam and collects them
from the view snapshot, exactly as `references` does. The `translate` function in
`module-host.mjs` — today the identity — becomes a lookup in the application's catalogue with
`%s` substitution, and `getLocale()` answers the request's locale instead of `"en"`. Same screen,
same button, rows instead of files.

**Strings every application shares.** Settings → Localisation links to **Translations (shared)**,
the same grid over the instance catalogue, with **Add a string** and **Translate missing**. On an
application's tab a key the shared catalogue covers is shown greyed with **override**, counts
towards coverage, and is skipped by **Translate missing**. MCP's `describe_translations` and
`save_translations` take `scope: "instance"`, and `feldspar i18n translate --instance` fills it
from a terminal.

### C — the user's own data

**Out of scope for this milestone**, as the brief says. The sketch, for the record: v1's
`localizes_field` becomes a field attribute (`localizes_field` + `locale`) on a String field; the
row layer projects the localised column in place of the base one when the request's locale matches
and the value is non-null. It lands in the same place a calculated field's projection does, and it
wants the read path designed rather than bolted on — which is why it is not here.

## 6. Where it lives

| Piece | Home |
|---|---|
| `Locale`, negotiation, `Catalog`, `format`, plural select, `t!`, `Translator` seam | **`sc-i18n`** (new crate, layer 0 — `sc-error` only) |
| Extraction and the lint (tree-sitter) | `sc-i18n`, feature `extract` |
| `core` catalogues | `crates/sc-i18n/locales/*.json`, embedded |
| Config keys, `users.language` | `sc-config`, `sc-auth` |
| Negotiation on a request, `Content-Language` | `sc-server::router` |
| Spec translation at the admin API edge | `sc-api::admin` handlers in `sc-server` |
| Per-application catalogues, `CatalogStore`, `_fd_translations` | `sc-app::i18n` |
| The shared catalogue and the app → instance merge | `sc-app::i18n` (`RowCatalogStore::instance`, `merged_app_catalogue`); its screen in `sc-server::translations` |
| `{mount}/i18n/{locale}.json` | `sc-server::router`, beside the observe socket |
| Generated `messages.ts` / `i18n.tsx` | `sc-app::scaffold::files` (common / React) |
| `Translator` over `sc-llm` | `sc-server`, `sc-cli` |
| `feldspar i18n extract\|lint\|check\|translate` | `sc-cli` |

`sc-i18n` at layer 0 is what lets `sc-auth` and `sc-types` call `t!` without a dependency
inversion. Everything that needs a database, a file store or an LLM is above it, behind a trait
declared in it — the arrangement `StreamProvider`, `Mailer` and `JsEvaluator` already have.

---

## 7. Limits, and what this does not do

- **No MessageFormat 2.** Right answer, wrong year: the Rust implementation is not there. The
  catalogue format is a flat JSON object, which is the format every one of these systems can be
  converted to and from, so the door stays open.
- **No XLIFF/PO import-export, no Weblate/Crowdin integration.** The JSON is trivially
  convertible and a converter is a script; wiring a TMS is a product decision, not a milestone.
- **No number, date or currency formatting in Rust.** The browser has `Intl`; the server has
  little reason to format a number for a human. Saltcorn UI's date fieldviews keep doing what
  they do.
- **RTL is a `dir` attribute and Bootstrap's RTL stylesheet**, not a layout audit. Arabic is in
  the shipped set precisely so the gaps are visible.
- **Translation is per installation, not per tenant**, because applications are the multi-tenancy
  (§13.2) and an application's catalogue is per application. The shared catalogue is the one
  level above that: an installation, never a group of applications.
- **The shared catalogue's languages are the installation's** (`enabled_locales`). An application
  can serve a language the admin UI does not, but it cannot inherit shared strings in it.
- **System errors stay English.**
- **Type C is not addressed.**
